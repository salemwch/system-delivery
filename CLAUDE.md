# Delivery Management Platform — Project Instructions

## Domain-first development

The domain model (docs/02-domain-model.md) is the source of truth. Read docs 01→02→03 before proposing any change. Never design tables before understanding the domain, never write business logic before defining rules, never create APIs before defining use cases. See the frozen domain model for entities, lifecycles, state machines, and invariants.

### Key design decisions (not derivable from code)

- `FIELD_ENCRYPTION_KEY` (base64 32 bytes) is REQUIRED — present in `.env`, placeholder in `.env.example`
- `shipment_events` partitioning deferred to keep unique constraints real (table is empty, retrofit is routine)
- Recipient counters are NOT written by shipment — they become a directory-side consumer
- `cod.collected` consumed by `ledger` group; `pod.captured` still published with no consumer
- DLQ replay/resolve admin path not built (rows land PENDING)
- Hub-ops commands (`arrived_at_hub`/`loaded`/`departed`) now live in `custody`. Custody transfers at manifest RECEIPT, never at seal (§3.11 rule 5). A RETURN manifest emits no `loaded` — its parcels are not at a hub
- Manifest hotspot H2 (who is liable for a missing parcel) is deliberately undecided — `manifest_discrepancies` records the facts and a resolution reason; no blame, no charge-back until the S2 policy call
- `custody` and `dispatch` are the only two sanctioned same-layer dependencies on `shipment`; both call it directly. `pickup` may NOT — it hands off via `pickup.parcel_scanned`
- **A GPS ping is NOT a business event** (event-storming §2.4, the single most important rule there). Raw telemetry never touches the outbox; only a geofence ENTER crosses into the business plane. A test asserts ingesting 20 batches produces zero `shipment.*` events
- `driver_positions` has **RLS + 90-day retention, NOT compression** — a deliberate deviation from 06-database-design §5.1. TimescaleDB 2.28 makes columnstore and row security mutually exclusive ("columnstore cannot be used on table with row security"); forced RLS wins on the most privacy-sensitive table in the system. Revisit at ADR-005's extraction trigger
- Migration ordering for a hypertable is load-bearing: table → hypertable → dimensions → **indexes → RLS → grants → compression/retention LAST**. Both `CREATE INDEX` and `ENABLE ROW LEVEL SECURITY` are rejected once columnstore is on
- `driver_positions.location` is a **GENERATED** column from `lon`/`lat`, so the point cannot be built wrong per call site and the writer stays a plain multi-row INSERT
- `TokenService.authenticate()` is the ONE implementation of "bearer token → Principal". Both `AuthGuard` and the WebSocket handshake call it, so a socket and a request can never disagree about identity
- Realtime backpressure policy: drop superseded `positions` frames, **never** `shipment_updated` or `alert`. A position is a sample the next one supersedes; a status change is a fact that happened once
- WebSocket fan-out goes through **Valkey pub/sub per tenant**, not in-process. Without it two API replicas means a dispatcher silently sees half the fleet — a bug that only appears on the second instance
- `@types/ws` is in `knip.json` `ignoreDependencies`: it is needed to resolve `@fastify/websocket`'s types, which knip cannot see
- **MERCHANT is the only role scoped BELOW the tenant.** Every other role sees the whole tenant, so RLS alone isolates it. A merchant sees only rows matching `users.merchant_id` inside a tenant that also holds rivals — enforced by RLS via `app.current_merchant_id` (migration 0020), never by a `WHERE` clause a query might forget
- A merchant token without `mid`, or a non-merchant token carrying one, is **rejected outright** by `TokenService` — a MERCHANT claim with no scope would read as "no narrowing" and see the whole tenant
- RLS predicates must use `CASE`, not `OR`: SQL does not promise to short-circuit `OR`, so `setting = '' OR col = setting::uuid` still evaluates `''::uuid` and errors
- A transaction-local `set_config` reverts to the **empty string**, not unset. A pooled connection reused with no context makes `current_setting(...)::uuid` a cast error — `deleteTenants` in the test harness sets `NO_TENANT` for exactly this reason
- `recipients` is tenant-scoped with no `merchant_id`, so MERCHANT deliberately holds **no** `recipient:*` permission — granting it would leak a competitor's customer list. Restore once the table is merchant-scoped (docs/02 §3.19)
- **RM-R1 is closed (2026-07-29): `recipients` stays tenant-scoped and merchants never read it.** One row per person is the point — history, address quality, and above all the repeat-refuser block-list have to accumulate across the tenant, and a per-merchant book splits all three. It is also not implementable: measured on PG 18, with the conflicting row hidden by a SELECT policy, `INSERT` gives 23505, `ON CONFLICT DO UPDATE … RETURNING` gives **42501**, `DO NOTHING … RETURNING` gives no id, and `UPDATE … WHERE phone` matches 0 rows — so a merchant could never create a parcel for an existing buyer. Merchants use `GET /v1/address-book`, a projection of their own shipments (already narrowed by 0020). See migration 0021
- **`mfa_enabled` used to lie, and the fix has a deadlock in it.** The flag was set true at provisioning so privileged accounts could log in at all — no enrolment, no challenge, so OWNER/FINANCE/PLATFORM_ADMIN were password-only. Now real: but a role in `MFA_REQUIRED_ROLES` cannot log in until enrolled and cannot enrol without a session. Broken by issuing a **challenge token alongside `MFA_ENROLMENT_REQUIRED`** — it authorises enrolment on one account for five minutes and nothing else. `verifyAccessToken` rejects `typ: "mfa"`, and `verifyMfaChallenge` rejects an access token, so the two can never be confused
- **The phone that logs a driver in lives on `users`, not on `drivers`.** Resolving phone → `drivers` → `users` would make `identity` (layer 0) depend on `fleet` (layer 1), and the port-and-adapter workaround produced a circular module reference. `users.phone` already existed, authentication identity is an identity concern, and `drivers.phone` stays the operational contact number — the two may legitimately differ. Partial UNIQUE on `(tenant_id, phone) WHERE phone IS NOT NULL`
- **OTP request must answer identically for a known and an unknown number.** Only the SMS is conditional. A different response — including a different rate-limit shape — lets anyone enumerate a courier's fleet one number at a time. `verify` also checks the code BEFORE resolving the driver, or the ordering itself answers the question
- **A TOTP code must be single-use, not merely valid.** A code stays good for its whole 30-second step plus drift, so one captured by a phishing proxy is replayable. `users.mfa_last_step` records the highest step accepted; anything at or below it is refused. Consequence for tests: enrolment consumes the current step, so a follow-up verification must use `currentCode(secret, 1)`
- **`audit_log` is append-only, and the REVOKE is what makes it so.** `initdb`'s `ALTER DEFAULT PRIVILEGES` grants `dp_app` full DML on every table `dp_migrator` creates, so `GRANT SELECT, INSERT` alone is a **no-op that reads like a restriction**. Each new partition needs the same REVOKE — privileges are checked on the table named in the query, so `DELETE FROM audit_log_202608` would otherwise bypass the parent. A trigger backs both up and catches the table owner, whom grants do not restrain
- **The audit trigger must let a tenant cascade through.** Deleting a tenant cascades to `audit_log`, and a blanket DELETE rejection blocks tenant deletion entirely. The trigger permits a delete only when the tenant row is already gone — a cascade fires after the parent is removed. Same pattern as the I14 manifest trigger
- **`AuditService.record` takes the caller's transaction**, exactly like `OutboxService.publish`. A trail written in its own transaction survives a rolled-back action and claims something happened that did not
- **A serialised flush must loop, not just await the in-flight one.** `TelemetryWriter.flush()` awaited the running flush and returned — but that flush had already taken the buffer, so rows enqueued in between stayed in memory while the caller was told everything was written. On `onApplicationShutdown` that silently discarded the last positions of every driver's trail. Surfaced as a flaky "19 of 20 positions" failure only under full-suite load
- **The flush fix above was HALF a fix, and the same flake came back.** Looping is necessary and an empty buffer is still not a safe exit. Two flushers is the ORDINARY case — the interval timer plus a caller — and when the first write settles both loops resume in one microtask batch: the timer's goes first, synchronously takes the whole buffer for its next write and suspends, so the caller resumes, sees an empty buffer and returns while those rows are still in flight. The exit condition is **no flush in flight AND nothing buffered**, never either alone. The original test hid it by awaiting BOTH promises with `Promise.all`; a caller only ever holds its own, and `onApplicationShutdown` awaits exactly that one before the process exits
- **A green `pnpm sast` can be a lie: never pipe a gate to `tail`.** In a shell pipeline the exit status is the LAST command's, so `pnpm sast | tail` reports `tail`'s success and two blocking Semgrep findings read as green for several increments. Redirect to a file and check `$?`, or run the gate bare
- **The money rule matched `CODE`.** `no-hardcoded-currency-scale` gated on `(?i).*cod.*`, and `cod` is a substring of CODE, encoded, decoded, codec — so `CODE_TTL_SECONDS * 1000`, an ordinary seconds-to-milliseconds conversion, was flagged as a 1000x money error. Now `cod(?!e)`. A rule that fires on non-money is one people learn to scroll past, which costs more than the rule was worth; both rules were re-verified against a probe file that genuinely violates them
- **A role allow-list written by hand will drift, and it drifts silently.** `AuthService.rolesOf` filtered against a hardcoded array that predated MERCHANT, so every merchant login authenticated with **zero roles and therefore zero permissions** — a portal that 403s on every request while the token looks valid. Both `rolesOf` and `UserService` now narrow through `isRole`, which derives from `ROLES`. Any future role must be added in exactly one place
- **The SMS provider is deliberately vendor-neutral.** Aggregator selection is an open business decision (MVP-O1), so `HttpSmsProvider` posts a generic JSON body (`to`/`from`/`text`) with Bearer or Basic auth, and reads the message id from any of `messageId`/`message_id`/`id`/`sid`. A 2xx with no id still counts as accepted — failing there would retry a message that already went out
- **Both notification channels default to `console`.** The fail-safe direction is "did not send", never "sent to production numbers from a staging box"
- **FCM without `firebase-admin`.** The package pulls a large tree to mint a service-account JWT and POST one endpoint — both a few lines of `node:crypto` + `fetch`. Token refresh is serialised so a fleet-wide dispatch mints one token, not twenty (Google rate-limits issuance)
- **Arabic SMS costs 70 characters per segment, not 160.** One non-GSM-7 character forces UCS-2 for the whole message, so a natural-reading Arabic template is easily three segments. `estimateSegments` exists so a template edit that triples the per-message cost fails a test instead of appearing on an invoice. Note `é` IS in GSM-7 — French copy stays cheap
- **`TelemetryWriter` drops a failed group rather than re-buffering it** — deliberate, documented, and the reason a test asserting an exact row count must check `stats().failedFlushes` first. Otherwise a contended telemetry pool surfaces as an inexplicable off-by-one instead of as a flush failure
- **`allowsReattempt` was defined and never consulted.** A parcel the customer had explicitly REFUSED consumed its two remaining attempts before returning — each a driver making a trip to someone who had already said no, plus the return leg. `decideReattempt` now checks the REASON before the attempt count. Fails OPEN on an unknown code: refusing to retry over a typo would strand a deliverable parcel, and the cap still bounds it
- **RETURN_PENDING and RETURNED were both reachable in the state machine and NOTHING COULD REACH RETURNED.** There was no command. A returning parcel could never be closed out, so the merchant's view stayed "coming back" forever. `completeReturn` closes it, guarded by `shipment:deliver` — handing a parcel back is a custody transfer by the driver who carried it, not an edit a dispatcher makes
- **A returned or cancelled COD needs `cod_status = 'CANCELLED'`, and this was a daily money error.** PENDING is what `shipment-stats` sums into cash-in-field (§4.5 #5.5) — the figure a courier reconciles its drivers' satchels against — so every returned COD parcel inflated it by its full value, permanently, in the direction that reads as "the driver is short". With normal COD return rates the reconciliation was simply wrong every day. NOT_APPLICABLE cannot be used: I6 ties it to a **zero amount**, and zeroing the amount destroys the record of what was at stake, which is the one number a merchant dispute turns on. CANCELLED keeps the amount and says the cash is closed (migration 0027)
- **Most returns are decided by the reason policy, not by a dispatcher, so the automatic path is the COMMON one.** It reached RETURN_PENDING without planning a RETURN leg (§3.7 rule 6, "never leaves the shipment legless") and without a notifiable payload — a parcel nobody could route back, about which nobody was told. Both paths now go through `spawnReturnLeg` and carry the same self-contained fields
- **Notification routes must be keyed on the EVENT name, never the status name.** A route read `shipment.return_pending` — the STATUS — while the publisher emits `shipment.return_initiated`. Nothing matched, so a customer was never told their parcel was going back, and the test agreed with the handler because both were wrong the same way. The test now derives names from `outboxEventName()`, which is the only version of that assertion that can fail
- **`sla_templates` allowed a service level no shipment can have.** The CHECK read STANDARD|EXPRESS|**SAME_DAY** while `shipments.service_level` allows EXPRESS|STANDARD|**SCHEDULED**, and a 0026 comment claimed they matched. SAME_DAY rows could never apply; SCHEDULED shipments had no template, so they got no promised-by date and silently fell back to a hardcoded 24-hour re-attempt delay instead of the tenant's own. Two CHECKs describing the same vocabulary must be diffed, not assumed
- **Scheduling is in WORKING hours, never elapsed.** A parcel accepted at 17:00 Friday with a 24-hour promise is due Monday. Measured in wall-clock time it would be late before anyone could have delivered it, on a day the courier is shut. `weekendDays` was hardcoded `[6,7]` — wrong for the Gulf, which runs Friday–Saturday
- **Working hours are LOCAL wall-clock, not UTC.** A courier opens at 08:00 Tunis time all year; storing UTC shifts the working day whenever the offset changes. `Intl.DateTimeFormat` does the conversion — hand-rolled offsets are how "one hour out for three weeks a year" happens
- **A migration that seeds cross-tenant rows must do so BEFORE enabling FORCE RLS.** One statement inserting a row per tenant cannot satisfy a single-tenant `WITH CHECK`, so every row is rejected and the migration rolls back. Same class of ordering trap as the TimescaleDB rule in 0018. Cost me one failed migration in 0026
- **A migration cannot back-fill a FORCE-RLS table, and it fails SILENTLY.** FORCE binds the table owner, and `dp_migrator` owns every table. A migration has no `app.current_tenant_id`, so every policy evaluates false and a back-filling `UPDATE`/`DELETE` matches **zero rows while reporting success**. `ADD CONSTRAINT` in the same file then validates the whole heap — RLS does not filter validation — and fails on precisely the rows the DML was supposed to have fixed. That mismatch is the diagnosis: DML is filtered, constraint validation is not. `SET LOCAL row_security = off` is not the escape (without BYPASSRLS it raises rather than exempting); `NO FORCE` … `FORCE` inside the file is, because each migration file is one transaction. Found in 0027, and the mirror image of the 0026 trap below
- **Seeding per-tenant defaults in a migration is a TIME BOMB.** `CROSS JOIN tenants` reads as "every tenant" and means "every tenant that existed at deploy time". 0026 seeded the failure taxonomy that way, so every courier onboarded afterwards had an empty one — `decideReattempt` found no `CUSTOMER_REFUSED` row, failed open as designed, and drove out twice more to someone who had already said no. Exactly the waste the module was built to stop, reintroduced by where the data lived. Defaults now live in `platform/domain/operating-defaults.ts` and `TenantService.provision` seeds them in the provisioning transaction; the migration is only the back-fill for tenants that already exist. **The test harness seeds from the same constants** — a test tenant without them exercises behaviour no production tenant will ever have
- **`z.record(z.enum([...]), …)` demands EVERY enum key.** A tenant supplying only French and Arabic labels was rejected. Use an explicit optional-keys object plus a non-empty refine when a subset is legitimate
- **Resolve and discard are different things in the DLQ, deliberately.** Resolve means the effect was achieved another way (a manual ledger correction); discard means it will never happen and demands a reason. Six months later that sentence is the only thing distinguishing written-off work from an unnoticed bug
- **DLQ replay checks `processed_events` FIRST.** A failure AFTER a handler's effects committed still dead-letters, so replaying blind would double-post a `cod.collected`. It marks the row resolved instead of re-running
- **`REPLAY_HANDLERS` is a separate token from `EVENT_HANDLER`.** The latter is single-valued and bound only in the worker; overloading it would break the API's dependency graph. Replay handlers are a list, optional, and bound in `app.module` — the API never consumes the stream, so they run only when an operator presses replay
- **Terraform targets DigitalOcean** (docs/09 §2 chose it for MVP, AWS at V2). Only `modules/` names a `digitalocean_*` resource, so the V2 migration is new module implementations behind the same interfaces. Staging keeps production's SHAPE — two app droplets and a two-node database — because one droplet never exercises the Valkey pub/sub fan-out behind the realtime feed
- **The cost function is INJECTED into one sequencer, not copied per solver.** Construction and 2-opt must consult the same costs — great-circle construction plus road-network improvement yields a tour optimal for neither, and both halves work so nothing looks wrong. With a matrix the duration is SUMMED from it, never distance ÷ a flat speed: that looks precise and still cannot tell a motorway from a medina alley
- **OSRM takes lon,lat and an unroutable pair comes back `null`.** Swapping the coordinates does not error — it routes in the Indian Ocean and returns plausible numbers. A `null` becomes `Infinity`, never 0 (which makes an impossible leg look free and attracts the tour) and never `NaN` (every comparison false, so 2-opt silently accepts nothing). A short row is rejected outright for the same reason
- **Money formatting lives in `shared/money`, not `finance`.** A delivery note prints a COD amount and `shipment` may not depend on `finance`, so the alternative was a second copy of `formatMinorUnits` — and the copy that drifts is the one that rounds TND to two places. `currencies` moved with it: the exponent is a property of the CURRENCY, the table is global with no `tenant_id` and no RLS, so there was nothing about it for a bounded context to own. finance still owns every table that records a MOVEMENT of money
- **Delivery documents render print-ready HTML, never generated PDF bytes.** Arabic needs bidirectional layout AND contextual glyph shaping (a letter has different initial/medial/final forms). Browsers do both natively; `pdfkit` and `pdf-lib` do neither, so Arabic through them is disconnected letters in left-to-right order — paperwork a Tunisian customer cannot read. Browser Print-to-PDF makes the PDF. Tracking numbers and E.164 phones carry `unicode-bidi: isolate` so they stay LTR inside an RTL page; mirrored, they get read back to a call centre wrong
- **A bon de retour is refused unless the parcel is actually returning.** RETURN_PENDING or RETURNED only — otherwise it is a forgery with a letterhead, signed by a merchant as proof they took back a parcel still out for delivery
- Parcel QR encodes the **bare tracking number** — not a URL, not JSON — so a scanned label drops straight into the existing scan endpoints, stays sparse, and carries no hostname
- **A `@Global()` module still has to be IMPORTED once, and the API had never booted.** `ValkeyModule` was registered only in `worker.module.ts`, so nothing provided `VALKEY_CLIENT` in the API graph and `tracking` failed to resolve at startup. Global means other modules need not re-import it, NOT that it registers itself. 843 tests passed throughout because they construct services by hand — no test ever started the Nest application. Found the first time a load test tried to talk to a running API
- **A user id is NOT a driver id, and telemetry conflated them.** The controller passed `principal.userId` to a parameter expecting `drivers.id`, so the shift lookup never matched and EVERY upload from a real authenticated driver was refused with `TELEMETRY_OUTSIDE_SHIFT` — GPS tracking was non-functional over HTTP. The unit tests missed it by calling `ingestBatch` directly with a driver id, which no request can do. Now `openShiftForUser` resolves the driver INSIDE the shift query: one join instead of two round-trips on the hottest endpoint in the system, and the fixture creates the `users` row so the mismatch is representable
- **Measured, not assumed (see [load/README.md](./load/README.md)).** Ingest at the MVP fleet is 24.7 ms p95 against a 300 ms budget; the box tops out near 112 req/s ≈ 1,125 positions/sec. A 40-stop optimisation takes 118 ms and leaves the board at 12 ms p95 while five run concurrently — ADR-005's accepted CPU risk does not materialise at the documented cap. Realtime coalescing is exactly 1.000 frames/sec/client with 200 drivers moving, where a naive fan-out would be 200. **10k positions/sec is NOT demonstrated** and must not be assumed
- **A k6 `Rate` that only records success measures nothing.** `subscribe_ok` called `.add(true)` on confirmation and nothing otherwise, so a session that never subscribed vanished from the metric instead of failing it — silence read as success. Recording one result per session immediately surfaced a real defect — see the handshake race below, which was invisible until the metric could express failure
- **The PUBLIC TRACKING PAGE COULD NEVER RESOLVE A TENANT.** `tenants` is FORCE RLS with `USING (id = current_setting('app.current_tenant_id'))`, and `resolveBySlug` is called by the unauthenticated tracking endpoint precisely to DISCOVER which tenant a request belongs to — before any context exists. The policy matched nothing, so every request answered "Tenant not found" and the whole customer-facing feature was dead. Chicken-and-egg: the id is needed to read the row, and the read is how you learn the id. Fixed with `resolve_tenant_id_by_slug`, a SECURITY DEFINER function exposing exactly one mapping (public slug → uuid, ACTIVE only) — deliberately not a broader RLS policy, because RLS is ROW-level, so "readable by anyone" would also expose every tenant's name, plan and status. Migration 0029, and note the mandatory `SET search_path`
- **Locale belongs in the PATH, not a query parameter.** A Next App Router layout cannot read `searchParams`, and `dir`/`lang` must sit on `<html>` for the document to mirror — so `?lang=ar` cannot produce an RTL page at all. `/[locale]/[tenantSlug]/[trackingNumber]` also makes the language switcher three ordinary links with zero JavaScript
- **`en-GB` is not a 24-hour clock unless you say so.** With `hour: "2-digit"` and no `hourCycle`, ICU rendered an arrival window as "02:10 PM" in English beside "14:10" in French and Arabic. Tunisia uses 24-hour time in all three; `hourCycle: "h23"` is explicit everywhere
- **A WebSocket's `message` listener must be attached SYNCHRONOUSLY, before the handshake is awaited.** `handleConnection` was `async` and registered `socket.on("message")` only after `await gateway.accept(...)` resolved. Every real client sends `subscribe` the instant the socket opens, so a frame landing in that window had no listener and was discarded by `ws` — silently. The client saw a socket that opened normally, never got `subscribed`, and never got a position: a dispatcher board that stays empty with nothing in any log. Worst on the FIRST connection for a tenant, where `accept` also waits on a Valkey SUBSCRIBE round-trip. Measured at 1 connection in 20; now 60/60 across three runs. Early frames are queued and replayed in arrival order, and the queue is capped because anything buffered pre-authentication is memory an unauthenticated peer can ask for
- **Nominatim's `format=jsonv2` renames `class` to `category`, and reading the wrong one fails SILENTLY.** The provider scored granularity off `place.class`, which is `undefined` in jsonv2 — so every address scored the unknown-class 0.4, landed below the 0.7 auto-dispatch floor, and the whole platform would have quietly stopped auto-dispatching with nothing in the logs. Every unit test passed, because the stubs were written from the same wrong assumption as the code. Only a query against a live instance found it; both names are now accepted
- **Geocode confidence comes from GRANULARITY, never Nominatim's `importance`.** `importance` is a PageRank-ish prominence score, so a famous city ranks high on a vague query — exactly backwards. A building or house-number match clears the floor; a `boundary` match is a whole governorate and must not
- **The geocoder chain falls through on LOW CONFIDENCE, not merely on null.** A provider returning a governorate centroid for a street address has 'succeeded' and produced a coordinate that sends a driver into the middle of a city. Nominatim runs first (free, and the address never leaves the deployment); a commercial provider is only reached for what it cannot place, so the bill tracks the hard addresses rather than the volume
- **`countrycodes` on every geocode is load-bearing.** Without it 'Ariana' matches a town in Iran and returns a perfectly plausible coordinate that nothing downstream questions
- **OSRM is bound (3.4), off by default.** `ROUTING_OPTIMIZER=haversine` unless a prepared extract exists — `pnpm osrm:prepare` then `pnpm osrm:up`. One `/table` call per optimisation, never one `/route` per pair: sequencing 25 stops touches hundreds of pairs, so per-pair calls are minutes of latency and one dispatcher saturating OSRM. **Every failure degrades to the haversine sequencer and sets `usedFallback`** — a dispatcher must always get a route (domain §3.9 rule 8), and the flag is what makes a permanent degradation visible instead of merely survivable

### Traps — read before modifying any module

**See [docs/traps.md](./docs/traps.md)** for the full reference. Critical ones:

- `set_config(…, true)` not `SET LOCAL`. Drizzle errors: walk `.cause` chain. PostGIS: never select raw geography column. `REVOKE` for restrictions (not narrower `GRANT`). Don't bind `Date` in raw `sql` fragments. Don't pass JS arrays to `= ANY($1::uuid[])` — use `inArray()`. Events must be self-contained (no cross-module lookups in consumers). OTel instrumentation = bare side-effecting import as first line. Finance accounts are lazy by owner. Ledger zero-sum is a DEFERRABLE trigger. Never re-export a `@Module` from a barrel.

## Engineering standards — non-negotiable

### Correctness

- **Ship production-ready code.** No `TODO`, no `FIXME`, no stubs, no placeholder returns.
- **Cover every path.** Valid, invalid, empty/null/boundary, concurrent, partial failure, timeout, retry, offline.
- **Every error handled deliberately.** No bare `catch {}`.
- **Verify before claiming done.** Run lint, types, and tests.

### Types

- **`any` is banned** (enforced by lint). Use `unknown` + narrowing.
- **No type assertions to escape problems.** Never `as any`, never `as unknown as T`.
- **Named types for domain values** (`TenantId`, `AmountMinor`, `TrackingNumber`).
- **No `!` non-null assertions.** Handle the null case.
- **TypeScript strict mode** + `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, etc. Do not weaken.

### One tool per job

| Job           | Use                             | Never alongside                 |
| ------------- | ------------------------------- | ------------------------------- |
| Validation    | **Zod**                         | class-validator, Joi, Yup       |
| Data access   | **Drizzle ORM**                 | Prisma, TypeORM, Knex           |
| HTTP          | **NestJS + Fastify**            | Express adapter                 |
| Jobs          | **BullMQ** (Valkey)             | node-cron, setInterval          |
| Events        | **Outbox → Valkey Streams**     | Kafka (until V2), EventEmitter2 |
| Cache         | **Valkey**                      | Redis duplication, Memcached    |
| Testing       | **Vitest** + **Testcontainers** | Jest, mocked repos              |
| HTTP client   | **native `fetch`**              | axios, got                      |
| Logging       | **Pino**                        | Winston, console.*              |
| Config        | **Zod-validated ConfigService** | direct process.env              |
| IDs           | **UUIDv7**                      | uuid package, nanoid            |
| Passwords     | **argon2 (Argon2id)**           | bcrypt                          |
| Money         | **bigint minor units**          | decimal.js, floats, ×100        |
| Observability | **OpenTelemetry**               | custom trace headers            |
| Routing       | **OSRM** behind adapter         | direct Google/Mapbox calls      |

Adding alternatives requires an ADR in `/docs`.

### Performance

- No N+1 queries. Every list paginates. Every external call has timeout + circuit breaker.
- Prefer faster/simpler when correctness is equal.

### Security

- Zod `strict` mode at boundaries. Parameterised queries only. No secrets in code.
- Never log PII. Every mutating endpoint: authenticated, authorized, ownership-checked, idempotent.

## Architecture summary

- **NestJS modular monolith** (`core-api` + `core-worker`). Go/Python specialists deferred (ADR-005).
- **Tunisia/MENA market.** COD is P0. Arabic/French/English, RTL first. **TND = 3 decimal places** — read exponent from `currencies`, never ×100.
- **Android-only driver app** at MVP. No iOS.
- **No AI/ML.** Deterministic substitutes only (OSRM, historical-median SQL, rule-based).
- **PostgreSQL 18 + PostGIS** system of record. Valkey for ephemeral state. No MongoDB.
- **Transactional outbox → Valkey Streams** (MVP) → Redpanda (V2). Publishers never know consumers.
- **Custody = append-only event log**; `shipments.status` is a derived projection.
- **Tenant isolation = PostgreSQL RLS**, not application code alone.
- **No Kubernetes, Kafka, MQTT at MVP** — complexity deferred with numeric triggers.

## Non-negotiable conventions

- Money: **integer minor units + ISO 4217 currency**. Never floats.
- Time: **TIMESTAMPTZ in UTC**; locations carry IANA timezone.
- Units: distances in **metres**, durations in **seconds**.
- IDs: **UUIDv7** externally. No exposed sequential integers.
- Every tenant-scoped table: `tenant_id NOT NULL` + forced RLS.
- Tenant context: **`SET LOCAL`** inside request tx — never `SET`.
- Every mutating endpoint: **`Idempotency-Key`**.
- Events: `tenant_id`, `event_id`, `correlation_id`, named `domain.fact` past tense.
- Every consumer: **idempotent on `event_id`**.
- Cross-module imports: **forbidden** (lint-enforced). Import from barrel only.
- No business logic branching on literal `tenantId` — use `TenantFeature` flags.
- UI: **CSS logical properties only** (`ms-4`, never `ml-4`).
- **Pin all versions.** No `latest`, no floating ranges.
- No secrets in repo, images, or committed env files.
