# Infrastructure as Code

Terraform for every cloud resource, from MVP onward
([docs/09-infrastructure.md](../../docs/09-infrastructure.md) §7). Click-ops
infrastructure cannot be reproduced, reviewed, or disaster-recovered — a
production estate nobody can rebuild is an outage waiting for its cause.

## Target: DigitalOcean

Per docs/09 §2, which compared five providers and chose **DigitalOcean for MVP,
AWS from V2**. At Tier 1 the constraint is engineering velocity, not managed-
service depth, and DO's managed PostgreSQL and Valkey cover what this platform
needs at roughly half the AWS cost.

The layout below keeps that migration honest: environments compose _modules_, and
the modules are the only place a `digitalocean_*` resource appears. Moving to AWS
is a new set of module implementations behind the same interfaces, not a rewrite
of every environment.

## Layout

```
infra/terraform/
├── modules/
│   ├── network/     VPC, firewalls, load balancer
│   ├── database/    Managed PostgreSQL (PostGIS + TimescaleDB) and Valkey
│   ├── compute/     Application and compute droplets
│   └── storage/     Spaces bucket for POD media
└── environments/
    ├── staging/
    └── production/
```

## State

Remote backend with locking, per docs/09 §7. State is **not** in this repository
and never will be: it contains database connection strings and generated
passwords in plaintext.

Each environment declares its own backend in `backend.tf`. The bucket must exist
before the first `init` — creating it in Terraform would be a chicken-and-egg
problem, so it is the one resource made by hand, documented here.

```bash
# Once per environment, before the first init.
doctl compute cdn create --help   # (see docs/09 for the bucket naming convention)
```

## Usage

```bash
cd environments/staging
terraform init
terraform plan -out=tfplan     # review — always
terraform apply tfplan
```

`plan` output is reviewed in a pull request before any apply. `apply` from a
laptop against production is not a workflow; it is an incident with a delay.

## Secrets

No secret is ever written to a `.tf` file or committed. Every credential is
either:

- generated by Terraform and stored only in state (database passwords), or
- injected at apply time from the CI secret store (`TF_VAR_do_token`).

`terraform.tfvars` is git-ignored for exactly this reason.

## What is deliberately NOT here

**Kubernetes.** docs/09 §4.2 defers it to V2 with a numeric trigger. Three VMs
and Docker Compose is the correct amount of machinery for Tier 1, and a cluster
nobody needs is a second system to operate.

**The Go and Python services** from the docs/09 topology diagram. ADR-005 defers
them; `core-api` and `core-worker` are the same image with different entrypoints,
so the compute droplet exists only for OSRM.
